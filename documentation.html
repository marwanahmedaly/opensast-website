Your first scan

Follow seven steps from installation to your first reviewed scan. All instructions are on this page.

Start with one Python project

OpenSAST checks Python source code for suspected security problems, then uses a local language model to review the relevant code. You inspect the resulting alerts in a dashboard.

This walkthrough runs on the machine that holds the Python project. You need an account with access to the OpenSAST source repository. No documentation download is needed: commands and explanations are below.

Your path

Prepare → install → configure → check readiness → register → scan → review.

Start step 1 · Already have a company installation?
What does it detect, and what are its limits?

The research targets path traversal (CWE-22), command injection (CWE-78), cross-site scripting (CWE-79) and SQL injection (CWE-89). Native Python and selected Flask patterns are primary; other framework support is partial or exploratory. A clean scan is not proof that the project is secure.

Step 1 — Prepare the scan machine

Where: a terminal on your Linux x86-64 scan machine. If you are using a remote machine, run the commands there.

uname -sm
python3 --version
git --version
df -h .

You need Python 3.11.8+ or 3.12+, its venv module, Git, and the Linux flock utility. Allow space for the application, CodeQL, scan data and the model. The optional default model alone is about 17.4 GB; the application and CodeQL checks reserve only their own space.

Before you continue: You have a compatible Linux machine, source-repository access and enough storage.

If it does not work: Ask your machine administrator for missing prerequisites. If your company already serves a compatible model internally, you can select that instead of downloading weights in step 3. See requirements.

Do I need a GPU?

Local CPU inference is supported but can be slow. The default model’s 24 GiB memory check is a provisioning heuristic, not a guaranteed hardware requirement or speed promise. For constrained machines, ask your administrator about an internal inference endpoint.

Step 2 — Get and install OpenSAST

Where: a directory where you keep tools, separate from the Python project you will scan.

curl -fsSL https://raw.githubusercontent.com/marwanahmedaly/opensast/main/scripts/install.sh | bash

Or clone the public repository and run the installer from its root. You can inspect the installer before running it; see installation details.

git clone https://github.com/marwanahmedaly/opensast.git
cd opensast

If you already have the source checkout, open its root directory instead. It must contain scripts/install.sh. The source and installer are publicly available; no GitHub account or repository invitation is required.

bash scripts/install.sh

The installer creates an isolated application environment and opens the setup wizard. It does not need sudo.

Before you continue: The application installs and the setup wizard begins. Continue to step 3 in the same terminal.

If it does not work: If cloning fails, check network access and the repository URL. Run the installer from the cloned OpenSAST root directory. For venv, PATH or storage errors, use troubleshooting.

The guided installer is implemented and source-reviewed. A complete fresh-machine, offline and upgrade acceptance run is not yet established. Earlier scan tests do not validate these new provisioning paths.

Step 3 — Answer the setup questions

Where: the setup wizard opened by step 2. A model is the local AI component that reviews suspected findings.

  1. Analysis tools: let setup provision the pinned CodeQL tools, or give the paths to an existing installation.
  2. Model: choose the pinned Qwen download, a GGUF model file already on the machine, or an existing company-internal llama.cpp endpoint.
  3. Account: choose your administrator username and a private password. Keep these for the dashboard.
  4. Workspace: enter your team name. A workspace groups the projects that its members can access.
  5. Readiness: wait for the dashboard and model checks to finish.

On a new installation, setup saves the administrator’s CLI login privately. Existing accounts and project history are preserved; an existing installation may need a separate login.

Before you continue: Setup reports it is ready, or identifies the component that is unavailable.

If it does not work: To resume setup, run opensast setup. To change saved choices, run opensast setup --reconfigure. An ordinary chat-only API is insufficient: an internal endpoint must also support the template/tokenizer APIs. See endpoint requirements.

Step 4 — Check that services are ready

Where: a new terminal on the same scan machine. Opening a new terminal makes any installer PATH changes available.

opensast doctor

This checks the scanner assets, CodeQL packs, model/template/tokenizer endpoint and dashboard. Readiness means the components respond; it does not measure detection accuracy.

Before you continue: The required components are reported as OK, with no NOT READY component.

If it does not work: If the command is not found, check ~/.local/bin and reopen your shell. If managed services are stopped, run opensast start, then repeat opensast doctor. Use the reported error to choose the recovery steps.

Step 5 — Register the Python project

Where: the root of the Python project you want to scan, not the OpenSAST tool checkout. Replace /path/to/your-python-project with its actual location.

cd /path/to/your-python-project
opensast init --no-browser

If asked, choose a workspace from the displayed list by its number, name or actual ID. With one workspace it may be selected automatically. Guided setup normally starts a project worker: the background process on this machine that performs queued scans.

Before you continue: The terminal reports a registered project and dashboard address. In the dashboard, the project’s worker should become online.

If it does not work: If you are not logged in, run opensast login --username YOUR_USERNAME using the account from step 3, then repeat init. Do not guess workspace IDs. If the project is registered but the worker could not start, follow worker recovery before scanning.

Registration alone does not start a scan. Continue to step 6.

Step 6 — Run the first scan

Where: keep the terminal in the registered project root.

opensast scan --wait

The first scan analyzes the full repository snapshot, gathers code evidence and reviews discovered candidates with the model. --wait keeps the terminal waiting for the job. It does not start an offline worker.

Before you continue: The job leaves queued, runs and reaches a terminal state. Inspect the final state: completion can still include unresolved decisions.

If it does not work: If it stays queued, check the worker is online. If it fails, inspect the reported error and job recovery; do not repeatedly queue scans without correcting the cause.

To check from a second terminal in the same project:

opensast status

Runtime depends on the repository, candidate count and model hardware. There is no guaranteed scan duration.

Step 7 — Open and review the results

Where: a browser on the scan machine. Open http://127.0.0.1:8765 and sign in with the account created in step 3.

  1. Select the workspace and registered project.
  2. Open the completed job in Scan history.
  3. Open a finding and read its location, model verdict and code evidence.
  4. Check whether untrusted input reaches the selected operation and whether a defense applies.
  5. Record your own review as confirmed, dismissed or open.

Before you continue: You can inspect the scan’s findings, including unresolved results, and keep your review separate from the model decision.

If it does not work: If the page does not open on a remote machine, use the SSH instructions below. If the account cannot see the project, check its workspace membership. Use the results guide for verdict meanings.

I am using a remote machine without a GUI

In a terminal on your own computer, replace USER@HOST with your scan-machine login and keep this connection open:

ssh -L 8765:127.0.0.1:8765 USER@HOST

Then open http://127.0.0.1:8765 on your own computer. Company reverse-proxy access is covered in deployment.

Next — Rescan after an edit

After changing your Python project, run this from its root:

opensast scan --wait

A valid unchanged snapshot can reuse results. Changed scans still run repository-wide CodeQL and gather fresh context; only eligible verifier decisions are reused. “Incremental” does not mean only edited files are analyzed.
