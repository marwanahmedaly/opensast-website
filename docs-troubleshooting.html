Troubleshooting

Find the failing stage before changing configuration or resubmitting a scan.

New to OpenSAST? Follow the seven-step first scan guide. These pages explain the details when you need them.

Start with readiness

opensast doctor
opensast status

Check the registered project directory, logged-in server, workspace access and worker last-seen time. Inspect private installation/service logs and the affected worker run. Readiness checks are not accuracy tests. Remove credentials and confidential source before sharing diagnostics.

Common symptoms

SymptomWhat to check
opensast: command not foundOpen a new terminal; check ~/.local/bin is on PATH and the installer completed.
Workspace is not accessibleUse workspace list and select the actual name/ID or displayed index. Confirm membership and remembered backend; do not guess numeric IDs.
Worker offline; job stays queuedStart the saved services/worker on the registered checkout machine. Check the token, backend reachability and engine settings. Waiting does not launch a worker.
Unexpected host / originUse the configured browser origin or SSH forwarding. For company deployment set the exact HTTPS public URL and proxy Host; do not disable origin protection.
Inference/tokenizer readiness failsCheck model serving, served name, context capacity, allowed host and llama.cpp template/tokenize APIs. A chat-only endpoint is insufficient.
Model startup/download failsCheck RAM/GPU memory, disk, archive checksum, compatible llama-server/system libraries and drivers. Retry setup; resumable downloads retain .part files.
UNRESOLVED / SYSTEM_ERROROpen the evidence and worker logs. Distinguish missing context from timeout, serving or structured-output failures; do not treat these as safe.
Repeated scan performs no inferenceCheck unchanged inventory, successful baseline and exact cache identity. This may be valid incremental reuse.
Scan very slowCheck candidate count, full CodeQL work, inference throughput, CPU/GPU serving and broad invalidation. There is no fixed scan-duration guarantee.
Disk fills upWorker snapshots, model files, CodeQL databases and logs occupy disk. Back up required evidence and apply a deliberate retention policy; no automatic cleanup exists.
CI base ref/model errorFetch full target history; use a valid immutable model revision and keep state/output outside the checkout. Submodule baselines are unsupported.

Recover a failed job

A worker losing its heartbeat has a 180-second lease; after expiry the job is marked failed/cancelled on subsequent job access or claim. Fix the service/credential problem and explicitly queue a new scan. Jobs do not retry indefinitely.

Failed/cancelled scans retain the earlier successful baseline. If the backend accepted results but a worker could not save its local baseline, a later scan may safely repeat work. Preserve the relevant logs before changing storage. If credentials were rotated, import the replacement and restart that worker.

Prepare a useful issue report

Include the application/engine versions, operating system, serving mode, command without secrets, job state, affected CWE/rule, reproducible symptom and sanitized error excerpt. State whether a forced full scan differs from incremental behavior if you already have that evidence. Do not upload complete private snapshots, tokens, passwords or company model endpoints to a public issue.

Consult the command reference, the complete product reference and the complete installation reference.
